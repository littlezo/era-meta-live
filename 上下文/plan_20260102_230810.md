# 统一直播平台接入层完善计划（修订版）

## 1. 计划修订背景

在实施统一直播平台接入层的过程中，发现了一些初始计划中未考虑到的问题，如平台特定逻辑的处理、返回类型的统一、代理处理等。为了确保计划的顺利实施和取得更好的效果，需要对初始计划进行修订和完善。

## 2. 修订后的计划目标

1. **统一平台特定逻辑**：将各平台特定的流处理逻辑移至统一API服务中
2. **统一返回类型**：定义统一的`StreamConfig`接口，确保所有平台返回类型一致
3. **统一消息监听接口**：为所有平台提供统一的消息监听接口
4. **完善分类获取API**：为所有平台实现完整的分类获取逻辑
5. **统一代理处理逻辑**：将代理处理逻辑移至统一API服务中
6. **优化类型定义**：完善各接口的类型定义，确保一致性

## 3. 修订后的计划内容

### 3.1 统一平台特定逻辑

#### 3.1.1 质量规范化

- 将各平台的质量规范化逻辑移至统一API服务中
- 实现`normalizeQuality`方法，根据平台类型规范化质量参数

#### 3.1.2 状态判断

- 统一各平台的在线状态判断逻辑
- 实现`isStreamLive`方法，根据平台类型和返回状态判断直播是否在线

#### 3.1.3 URL处理

- 统一HTTPS强制转换逻辑
- 统一流类型推断逻辑
- 实现`processStreamUrl`方法，处理不同平台的流URL

### 3.2 统一返回类型

#### 3.2.1 定义统一的`StreamConfig`接口

```typescript
interface StreamConfig {
  streamUrl: string;
  streamType: string;
  title?: string;
  streamerName?: string;
  avatarUrl?: string;
  isLive: boolean;
  errorMessage?: string;
}
```

#### 3.2.2 统一错误处理

- 统一各平台的错误处理方式
- 要么都返回错误信息，要么都抛出错误
- 实现`handleError`方法，统一处理各平台的错误

### 3.3 统一消息监听接口

#### 3.3.1 统一方法名称

- 将各平台的消息监听方法名称统一为：
  - `startMessageListener`
  - `stopMessageListener`

#### 3.3.2 统一消息payload类型

- 定义统一的消息payload类型`UnifiedMessagePayload`
- 确保所有平台的消息格式一致

#### 3.3.3 统一消息处理逻辑

- 统一各平台的消息处理逻辑
- 实现`processMessage`方法，处理不同平台的消息

### 3.4 完善分类获取API

#### 3.4.1 为所有平台实现分类获取逻辑

- 斗鱼平台：已实现
- 抖音平台：需要实现
- B站平台：需要实现
- 虎牙平台：需要实现

#### 3.4.2 定义统一的分类数据结构

- 设计统一的分类数据结构`UnifiedCategory`
- 确保所有平台返回的分类数据格式一致

### 3.5 统一代理处理逻辑

#### 3.5.1 将代理处理逻辑移至统一API服务

- 实现`startProxy`和`stopProxy`方法
- 支持多平台代理处理

#### 3.5.2 实现代理状态管理

- 记录各平台的代理状态
- 避免重复启动/停止代理

### 3.6 优化类型定义

#### 3.6.1 完善各接口的类型定义

- 确保所有API方法的类型定义完整
- 确保类型定义的一致性

#### 3.6.2 移除平台特定的字段

- 使用统一的字段名称，如将`anchor_name`改为`streamerName`
- 确保所有数据模型使用统一的命名规范

## 7. 修订后的风险评估

### 7.1 平台差异风险

- **风险**：不同平台的API差异较大，统一处理难度增加
- **应对措施**：采用适配器模式，为每个平台实现特定的适配器

### 7.2 兼容性风险

- **风险**：修改返回类型可能导致前端兼容性问题
- **应对措施**：保持向后兼容，逐步迁移前端代码

### 7.3 性能风险

- **风险**：统一API服务可能引入额外的性能开销
- **应对措施**：优化统一API服务的实现，减少性能开销

### 7.4 测试风险

- **风险**：需要确保所有平台的功能在修订后正常工作
- **应对措施**：编写详细的测试用例，进行全面测试
