## 重构Platforms库实现统一RPC服务层

### 1. 重构目标
- 踢除platforms对tauri的依赖
- 设计统一的RPC服务层来抹平各直播平台API差异
- 设计统一的RPC client提供给tauri和前端调用
- 每个平台作为独立子包存在，方便扩展新平台
- 设计统一的平台接口来抹平平台差异和统一调用方式
- danmuke改名 为 message

### 2. 架构设计

#### 2.1 目录结构设计
```
platforms/
├── Cargo.toml                 # 主库Cargo配置
├── src/
│   ├── lib.rs                 # 主库入口
│   ├── rpc/
│   │   ├── server.rs          # RPC服务端实现
│   │   ├── client.rs          # RPC客户端实现
│   │   └── proto/             # 协议定义文件
│   ├── platform/
│   │   ├── mod.rs             # 平台接口定义
│   │   └── traits.rs          # 统一平台接口trait
│   ├── message/               # 原danmu模块，重命名为message
│   │   ├── mod.rs
│   │   └── types.rs
│   └── platforms/
│       ├── mod.rs
│       ├── bilibili/          # 哔哩哔哩平台实现
│       ├── douyin/            # 抖音平台实现
│       ├── douyu/             # 斗鱼平台实现
│       └── huya/              # 虎牙平台实现
└── examples/
    └── rpc_server.rs          # RPC服务端示例
```

#### 2.2 核心设计

1. **统一平台接口**
   - 定义`Platform` trait，包含所有平台需要实现的方法
   - 包含直播流获取、弹幕监听、房间信息获取等核心功能
   - 每个平台实现该trait，提供统一的调用方式

2. **RPC服务层**
   - 使用gRPC或JSON-RPC实现跨语言调用
   - 定义统一的服务接口，映射到平台接口
   - 支持异步调用和事件推送

3. **消息系统**
   - 将原有danmu相关代码重命名为message
   - 设计统一的消息格式，包含不同平台的消息类型
   - 支持消息订阅和推送机制

4. **平台管理**
   - 实现平台工厂模式，根据平台名称创建对应的平台实例
   - 支持动态加载新平台
   - 提供平台注册机制

### 3. 实现步骤

#### 3.1 第一步：移除tauri依赖
- 修改`/Volumes/Data/project/era-meta-live/src-tauri/platforms/Cargo.toml`，移除tauri依赖
- 重构commands.rs，移除tauri相关代码
- 确保平台库可以独立编译和运行

#### 3.2 第二步：设计统一平台接口
- 在`platform/traits.rs`中定义统一的Platform trait
- 包含以下核心方法：
  - `get_stream_url` - 获取直播流URL
  - `start_message_listener` - 启动消息监听
  - `stop_message_listener` - 停止消息监听
  - `get_room_info` - 获取房间信息
  - `search_rooms` - 搜索房间
  - `fetch_live_list` - 获取直播列表

#### 3.3 第三步：实现RPC服务层
- 选择合适的RPC框架（如tonic、jsonrpsee等）
- 定义RPC服务协议
- 实现RPC服务端，将请求转发到对应平台实现
- 实现RPC客户端，供tauri和前端使用

#### 3.4 第四步：重构平台实现
- 将每个平台实现迁移到独立的子包
- 实现统一的Platform trait
- 重构danmu相关代码为message模块
- 确保每个平台可以独立测试和扩展

#### 3.5 第五步：集成测试
- 编写单元测试和集成测试
- 测试RPC服务端和客户端的通信
- 测试各平台实现的功能
- 确保跨平台兼容性

#### 3.6 第六步：文档和示例
- 编写API文档
- 提供RPC服务端启动示例
- 提供RPC客户端使用示例
- 编写平台扩展指南

### 4. 关键技术点

1. **RPC框架选择**
   - 考虑性能、跨语言支持、易用性
   - 推荐使用tonic（gRPC）或jsonrpsee（JSON-RPC）

2. **异步编程**
   - 使用tokio作为异步运行时
   - 实现异步消息监听和处理
   - 支持异步RPC调用

3. **平台隔离**
   - 每个平台作为独立子包，避免耦合
   - 使用特征对象实现运行时多态
   - 支持动态加载新平台

4. **消息格式统一**
   - 设计通用消息结构体，包含平台特定字段
   - 支持消息序列化和反序列化
   - 实现消息类型转换机制

### 5. 预期成果

- 独立的Platforms库，无tauri依赖
- 统一的RPC服务层，支持跨语言调用
- 统一的平台接口，抹平各平台差异
- 每个平台作为独立子包，方便扩展
- 消息系统替代原有的danmu系统
- 完整的文档和示例代码
