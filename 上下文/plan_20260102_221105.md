# 统一直播平台接入层计划

## 1. 计划背景

当前项目中，各直播平台（Douyin、Douyu、Huya、Bilibili）的API调用采用了直接调用平台特定命令的方式，导致代码中存在大量平台特定逻辑，增加了代码维护成本和新平台接入难度。为了提高代码的可维护性和可扩展性，需要设计并实现一个统一的直播平台接入层。

## 2. 计划目标

1. **统一API接口**：设计一套统一的API接口，封装不同直播平台的特定实现
2. **平台无关设计**：使主应用和前端不再需要关心具体的直播平台实现
3. **简化平台接入**：降低新直播平台的接入成本
4. **提高代码复用性**：减少重复代码，提高代码质量
5. **增强类型安全**：完善类型定义，提高代码的类型安全性

## 3. 计划内容

### 3.1 设计统一API服务

- 创建`platformApiService.ts`文件，提供统一的API接口
- 实现单例模式，确保全局只有一个API服务实例
- 封装各平台的特定实现，提供统一的调用方式

### 3.2 统一API方法设计

| 方法名 | 功能描述 |
|--------|----------|
| fetchLiveList | 获取直播列表 |
| fetchRoomInfo | 获取直播间信息 |
| getStreamUrl | 获取直播流URL |
| fetchStreamerInfo | 获取主播信息 |
| searchRooms | 搜索直播间 |
| startMessageListener | 启动消息监听 |
| stopMessageListener | 停止消息监听 |
| checkRoomStatus | 检查直播间状态 |
| fetchCategories | 获取直播分类列表 |

### 3.3 统一数据模型设计

- 设计统一的房间信息模型`UnifiedRoomInfo`
- 设计统一的直播流信息模型`UnifiedStreamUrl`
- 设计统一的主播信息模型`UnifiedStreamerInfo`
- 设计统一的直播消息模型`UnifiedMessage`

### 3.4 迁移现有代码

- 将各平台的`playerHelper.ts`文件中的直接调用替换为统一API调用
- 移除平台特定的重复逻辑，移至统一API服务中
- 统一各平台的返回类型和错误处理方式

### 3.5 完善类型定义

- 完善各API接口的类型定义
- 确保类型定义的一致性和完整性
- 为所有平台消息定义统一的类型

## 4. 实施步骤

1. **设计阶段**：设计统一API接口和数据模型
2. **实现阶段**：实现统一API服务，封装各平台特定逻辑
3. **迁移阶段**：将现有代码迁移到统一API服务
4. **测试阶段**：测试各平台功能是否正常
5. **优化阶段**：根据测试结果优化统一API服务

## 5. 预期效果

- 主应用和前端不再需要关心具体的直播平台实现
- 新平台接入更加简单，只需实现统一API服务中的抽象方法
- 代码复用性提高，维护成本降低
- 类型安全保障增强，减少类型错误
- 代码结构更加清晰，便于后续扩展和维护

## 6. 风险评估

1. **平台差异风险**：不同平台的API差异较大，可能导致统一API设计难度增加
2. **兼容性风险**：迁移现有代码可能导致兼容性问题
3. **性能风险**：统一API服务可能引入额外的性能开销
4. **测试风险**：需要确保所有平台的功能在迁移后正常工作

## 7. 应对措施

1. **平台差异处理**：采用适配器模式，为每个平台实现特定的适配器
2. **兼容性保障**：保持现有API接口不变，逐步迁移到统一API服务
3. **性能优化**：优化统一API服务的实现，减少性能开销
4. **全面测试**：编写详细的测试用例，确保所有平台的功能正常工作

## 8. 交付物
