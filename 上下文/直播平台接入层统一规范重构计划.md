# 直播平台接入层统一规范重构计划

## 1. 统一规范目标

- **文件命名规范**：统一各平台文件命名风格，避免混乱
- **模块结构规范**：统一各平台模块组织方式，提高代码可维护性
- **函数命名规范**：统一函数命名模式，增强代码可读性
- **术语统一**：统一各平台使用的术语，如主播、直播间等
- **代码风格统一**：统一代码格式、缩进、注释等风格

## 2. 统一规范详细内容

### 2.1 文件命名规范

| 功能模块 | 统一文件名 | 说明 |
|---------|-----------|------|
| 直播列表 | live_list.rs | 获取平台直播列表 |
| 房间信息 | room_info.rs | 获取直播间详细信息 |
| 主播信息 | streamer_info.rs | 获取主播详细信息 |
| 弹幕消息 | message.rs | 弹幕消息监听和处理 |
| 流地址获取 | stream_url.rs | 获取直播流地址 |
| 搜索功能 | search.rs | 搜索直播间或主播 |
| 分类信息 | categories.rs | 获取平台分类信息 |
| 平台模型 | models.rs | 平台特定数据模型 |
| 认证功能 | auth.rs | 平台认证相关功能 |

### 2.2 模块结构规范

每个平台目录下采用统一的模块结构：

```
platform_name/
├── src/
│   ├── lib.rs          # 平台主实现
│   ├── live_list.rs    # 直播列表功能
│   ├── room_info.rs    # 房间信息功能
│   ├── streamer_info.rs # 主播信息功能
│   ├── message.rs      # 弹幕消息功能
│   ├── stream_url.rs   # 流地址获取功能
│   ├── search.rs       # 搜索功能
│   ├── categories.rs   # 分类信息功能
│   ├── models.rs       # 数据模型
│   └── auth.rs         # 认证功能
└── Cargo.toml
```

### 2.3 函数命名规范

统一函数命名格式：

```rust
// 平台特定功能函数
sync/async fn [action]_[platform]_[resource](...) -> Result<...>

// 示例
async fn fetch_bilibili_live_list(...) -> Result<...>
async fn fetch_douyin_room_info(...) -> Result<...>
```

### 2.4 术语统一

| 术语 | 统一使用 | 避免使用 |
|------|----------|----------|
| 直播间 | room | anchor_room, live_room |
| 主播 | streamer | anchor, owner, user |
| 观众数 | viewer_count | watching, hot, user_count |
| 直播状态 | live_status | status, is_live |
| 封面图 | cover_url | cover |
| 头像 | avatar_url | avatar |

## 3. 重构实施步骤

### 3.1 第一步：整理现有代码结构

1. **分析现有文件**：检查每个平台的现有文件，确定需要重命名或重组的文件
2. **制定映射表**：为每个平台创建现有文件到目标文件的映射表
3. **备份现有代码**：确保在重构前备份所有代码，防止意外丢失

### 3.2 第二步：统一文件命名

按照统一规范重命名各平台的文件：

| 平台 | 现有文件 | 目标文件 |
|------|----------|----------|
| Douyin | douyin_streamer_list.rs | live_list.rs |
| Douyin | douyin_streamer_info.rs | room_info.rs |
| Douyin | douyin_streamer_detail.rs | stream_url.rs |
| Douyin | douyin_message_listener.rs | message.rs |
| Douyu | fetch_douyu_room_info.rs | room_info.rs |
| Douyu | search_anchor.rs | search.rs |
| Douyu | fetch_douyu_main_categories.rs | categories.rs |
| Douyu | three_cate.rs | categories.rs |
| Douyu | types.rs | models.rs |
| Douyu | message_start.rs | message.rs |

### 3.3 第三步：统一模块结构

1. **调整模块组织**：确保每个平台的模块结构符合统一规范
2. **合并相关功能**：将分散在多个文件中的相关功能合并到一个文件中
3. **拆分复杂模块**：将过于复杂的模块拆分为更小的、职责单一的模块

### 3.4 第四步：统一函数命名

1. **重命名函数**：按照统一的函数命名规范重命名各平台的函数
2. **调整函数签名**：确保相同功能的函数具有一致的签名
3. **统一返回类型**：确保相同功能的函数返回类型一致

### 3.5 第五步：统一术语和风格

1. **替换不一致术语**：在所有平台代码中统一使用规范术语
2. **调整代码风格**：统一代码格式、缩进、注释等风格
3. **优化代码结构**：简化复杂逻辑，提高代码可读性

### 3.6 第六步：测试和验证

1. **编译测试**：确保重构后的代码能够正常编译
2. **功能测试**：测试每个平台的核心功能是否正常工作
3. **集成测试**：测试平台间的集成是否正常
4. **性能测试**：确保重构后的代码性能不劣于重构前

## 4. 重构注意事项

1. **避免破坏性变更**：尽量保持对外接口的兼容性
2. **逐步实施**：分阶段进行重构，避免一次性修改过多代码
3. **充分测试**：每完成一个阶段的重构，都要进行充分的测试
4. **保持文档同步**：及时更新相关文档，确保文档与代码一致
5. **遵循最小修改原则**：只修改必要的代码，避免不必要的变更

## 5. 预期成果

- 各平台代码结构统一，易于维护和扩展
- 代码可读性提高，降低新开发者的学习成本
- 功能模块清晰，便于后续功能扩展和bug修复
- 统一的命名规范，减少命名混乱和误解
- 提高代码质量和可维护性，为后续开发奠定良好基础

## 6. 重构优先级

1. 首先统一文件命名和模块结构
2. 然后统一函数命名和术语
3. 最后优化代码风格和结构

## 7. 实施时间安排

- **分析和规划**：1天
- **文件命名和模块结构统一**：2天
- **函数命名和术语统一**：2天
- **代码风格优化**：1天
- **测试和验证**：2天

## 8. 风险评估

- **编译错误风险**：重命名和重组文件可能导致编译错误，需要仔细检查和测试
- **功能回归风险**：重构可能引入新的bug，需要充分测试
- **接口兼容性风险**：如果修改了对外接口，可能影响其他模块的使用
- **时间风险**：重构可能比预期花费更多时间，需要合理安排进度

## 9. 解决方案

- **详细规划**：在实施前制定详细的规划和映射表
- **分阶段实施**：分阶段进行重构，每个阶段都进行充分测试
- **保持备份**：在重构前备份所有代码，以便出现问题时可以回滚
- **代码审查**：邀请其他开发者进行代码审查，确保重构质量
- **自动化测试**：使用自动化测试工具，提高测试效率和覆盖率

## 10. 后续维护

- 建立代码审查机制，确保新代码符合统一规范
- 定期检查代码，及时修复不符合规范的代码
- 更新开发文档，确保文档与代码一致
- 培训新开发者，确保他们了解和遵循统一规范

通过这次重构，我们将建立一个统一、规范、易于维护的直播平台接入层，为后续的开发和扩展奠定良好基础。
